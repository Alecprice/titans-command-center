# Titans Command Center

A mobile-first, installable Tennessee Titans fan HQ and data PWA. It combines current team information, game-day context, roster and transaction snapshots, free market-data adapters, player intelligence, franchise history, optional fan personalization, and Cloudflare D1-backed data services behind a custom Titans-focused UI.

## Current platform — app v1.0.0 / 2026 fan PWA

The project follows a **content-integrity first** model. Current facts are checked against TennesseeTitans.com first, then NFL.com where appropriate. The Pro Football Hall of Fame, Pro Football Reference, nflverse, SportsLogos.net and Wikipedia are secondary/cross-check sources by domain rather than interchangeable authorities.

### Production architecture

- GitHub `main` is the production source branch.
- Production deploys to a **Cloudflare Worker + Static Assets**; `/api/*` is handled by the Worker before static fallback.
- `wrangler.jsonc` is the authoritative runtime configuration and binds the production D1 database as `TITANS_DB`.
- **Cloudflare D1 is the production data authority.** Bootstrap data, account preferences, materialized intelligence/analytics snapshots, and scheduled audit/write records use D1.
- The retired Neon Postgres warehouse is not part of the production runtime and `DATABASE_URL` is not a deployment requirement.
- Neon Auth remains temporarily as a separate managed authentication service behind the narrow same-origin account proxy. It is not the application database and does not restore warehouse access.
- Cloudflare deployment runs the repository quality gate before deploy, then production API and browser regressions across navigation, Listen / Watch, Market Pulse, Command Intelligence, Player Intelligence / Game Day, Ask Titans, Change Intelligence, Runtime / 365 Mode, freshness, Account / Guest, analytics, and headshots.
- `docs/CLOUDFLARE_STATUS.md` is generated by the deployment workflow and records the most recent production deployment result.
- Any remaining Vercel configuration/check is legacy and non-authoritative for production. The active app is Cloudflare-hosted.

### Fan experience working now

- Installable PWA with phone, tablet/small-laptop, desktop, and wide-desktop layouts.
- Five-action mobile dock: Home, Roster, Game, Search, and More.
- 365 Mode changes home priorities based on the football calendar without pretending unofficial dates are league-defined windows.
- Smart search for players, jersey numbers, positions, weeks, roster moves, next home games, injuries, history, stats, and app sections.
- Customizable home command deck with reorderable/hideable game, favorite-player, roster-move, intel, market, and freshness cards.
- Player intelligence, favorites, position-aware comparison, schedule detail expansion, Game Day, analytics, market context, Listen / Watch, legacy navigation, and change intelligence.
- Optional accounts with guest-first access. Signing in is never required to browse the app.
- Selected signed-in preferences sync through D1 when authenticated; guest settings remain browser-local and auth/provider failures degrade safely to guest/local behavior.
- Browser/PWA reliability includes saved data fallback, offline messaging, pull-to-refresh, route recovery, scroll restoration, service-worker update handling, and production browser smoke coverage.
- API/auth responses are never PWA-cached.

### Audited football-data baseline

The repository keeps dated source assertions rather than silently presenting old snapshots as live facts.

- The current fallback roster is the Aug. 27 official audit and contains 95 players.
- Week 9 is the 2026 bye; Week 18 at Houston remains **TBD** in the audited schedule baseline and the official venue name used by the project is **Reliant Stadium**.
- Team Room includes dated official roster/depth information with ties and uncertainty preserved rather than inferred.
- Stats Lab separates verified prior-season baselines from not-yet-complete 2026 regular-season totals and exposes known source conflicts instead of filling gaps with guesses.
- The current visual treatment uses Titans Blue-led branding and verified current marks; historical/reference imagery remains separately labeled.

### Source checks vs. persistence

A reachable provider is **not** the same thing as a successful data refresh.

- The protected scheduled endpoint runs source checks and bounded reconciliation work rather than pretending every reachable provider produced new rows.
- Official Titans roster/transactions/schedule/depth-chart pages can receive reachability/marker checks without unverified HTML parsing into production data.
- Scheduled source-check outcomes and reconciliation diagnostics are persisted to D1 with success/skipped/failed semantics and records-seen/written kept separate.
- Skipped source checks do not count as successful refreshes.
- Provider loss does not authorize fabricated roster, injury, market, or analytics facts; dated audited or last-known D1 snapshots are used only where the API contract explicitly supports them.

## Source hierarchy

1. **Roster / schedule / transactions / staff:** TennesseeTitans.com, with NFL.com as official cross-check where applicable.
2. **Statistics:** structured Tennessee Titans team-stat tables first; NFL.com, Pro Football Reference and nflverse as cross-checks. Editorial recap copy does not override the structured table.
3. **Injuries:** official Titans injury report. Reserve/Injured roster status is separate, and “no report yet” never means zero injuries.
4. **History:** Titans official history plus the Pro Football Hall of Fame; PFR/Wikipedia are secondary.
5. **Visual identity:** Titans brand/history pages first, SportsLogos.net second. User-supplied art is reference material unless an exact mark/year is verified.

Known discrepancies are surfaced rather than hidden. See [`docs/CONTENT_INTEGRITY.md`](docs/CONTENT_INTEGRITY.md).

## Local development

```bash
npm install
cp .env.example .env.local
npm run dev
```

Open `http://localhost:4173`.

Local development does not require a Postgres connection string. Features that need a Cloudflare D1 binding use their explicit local-safe/audited fallback behavior when the binding is absent.

## Quality checks

```bash
npm run check
```

This runs Node regression tests, factual-content assertions, credential/secret scanning, recursive JavaScript/Python syntax checks, the Cloudflare build, and Cloudflare build verification.

## Cloudflare deployment

```bash
npm run deploy:cloudflare
```

Production deployment is normally handled by `.github/workflows/cloudflare-deploy.yml` after changes reach `main`. GitHub Actions requires the Cloudflare API token/account ID; optional provider credentials are added only when the corresponding integration is configured. `DATABASE_URL` is not read or uploaded by the deployment workflow.

D1 schema changes live under `db/d1/migrations` and can be applied with:

```bash
npm run d1:migrate
```

## Core API surface

Public and protected API routes are dispatched by `cloudflare/worker.mjs`. Core routes include:

- `GET /api/health`
- `GET /api/provider-health` — protected diagnostics
- `GET /api/data`
- `GET /api/fan-intel`
- `GET /api/espn-scoreboard`
- `GET /api/bluesky-search?q=...`
- `GET /api/odds`
- `GET /api/player?id=...`
- `GET /api/advanced-analytics?...`
- `GET /api/preseason-stats`
- `POST /api/sync?job=...` — protected
- `GET /api/cron-refresh` — protected scheduled source check
- `/api/account/auth/*` — narrow same-origin managed-auth proxy
- `GET|PUT /api/account/preferences` — authenticated D1-backed preference sync with explicit local-safe failure behavior

Legacy warehouse gateway routes remain explicit retired states where compatibility routing still exists; they are not database fallbacks.

## Free/no-card policy

Core dependencies should remain usable at $0 without entering a payment card where practical. Server credentials belong only in environment configuration and must never be committed or shipped to browser JavaScript.

## Data storage

Production persistence is Cloudflare D1:

- `fan_user_preferences` stores bounded authenticated preference JSON.
- `api_snapshots` stores materialized bootstrap/intelligence/analytics and operational snapshots.
- Scheduled writes use D1-only helpers and fail closed when D1 is unavailable.
- `db/d1/migrations/0001_core.sql` is the current portable D1 schema baseline.

The files under legacy `db/migrations`, `db/schema.sql`, and `db/seed.sql` describe the retired Postgres warehouse and are retained only as migration history until their separate archival/removal pass is complete. They are not executed by current production deployment.

## Authentication

Neon Auth is currently isolated behind `/api/account/auth/*` so the warehouse migration and authentication migration are independent. A future auth cutover may replace it with Better Auth + D1 while preserving the public account endpoint contract. Do not add `DATABASE_URL` or `@neondatabase/serverless` to implement account storage; preferences are already D1-backed.

## Branding

This is an unofficial fan-built project. Team/NFL marks remain property of their respective rights holders. `docs/BRAND_UI.md` separates current official identity facts from implementation accents and historical/reference artwork.
